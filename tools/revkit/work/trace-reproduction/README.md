# Reproducing pruned analysis artifacts

From the repository root, verify the GDB reconstruction recipes without
writing runtime outputs:

```sh
python3 tools/revkit/scripts/reproduce_artifacts.py verify --kind gdb
```

Restore a command file cited by a research document at its original path:

```sh
python3 tools/revkit/scripts/reproduce_artifacts.py restore --kind gdb \
  --path tools/revkit/work/stage21/trace-makeinfo-letter-vary-prefix-fixed-aa-b1.gdb
```

Omit `--path` to restore every manifest entry of the selected kind. Use
`--kind wav` for WAVE recipes, following the runtime instructions below. `--output-root /tmp/rebuilt-vtspeak`
restores under a separate directory while reading sources from this checkout.
`clean` removes only manifest outputs whose size and SHA-256 still match;
changed files are refused. Regenerated outputs stay ignored.

## GDB reconstruction sources

The manifest covers all **916** `.gdb` files present before this cleanup:

- **70** command files are generated by the pure Bash generators in
  `generators/`, extracted from the existing Stage 21 runners. These retain
  the original command-generation loops, remove runtime/environment setup,
  and use Bash builtins for ASCII conversion. Explicit case, batch, and resume
  parameters are recorded per output. The two quarantined incorrect case
  mappings use an explicit legacy flag; their historical contents are preserved.
- **2** command files use the existing Python CSV matrix generators.
- **844** command files use **793** distinct readable source templates in
  `sources/`. Identical scripts share a template. These preserve authored
  instructions and historical variants for which the current runner alone
  does not recreate the exact file. They are source instructions, not runtime
  captures. A `#@bytes` source directive expands a run of consecutive decimal
  GDB byte writes; its JSON fields are line prefix, starting offset, line
  suffix, and hexadecimal byte values. `#@literal` emits a JSON string verbatim
  where significant trailing whitespace or blank lines need preserving. All
  other lines are emitted verbatim.

Every reconstruction was compared byte for byte with the original file before
removal. The manifest records the original size and SHA-256, and the tool checks
both on every reconstruction. It refuses to overwrite an existing file with
different contents. Python 3 and Bash suffice to reproduce the command files;
the generator code does not launch Wine, GDB, Docker, or VoiceText.

Executing those commands to repeat a runtime observation still requires the
local proprietary binaries/models and the Docker/Wine setup in the toolkit
README. Follow the original stage's runner and working-directory instructions.
Runners that generate their own GDB file may refuse to overwrite a materialized
copy; use `clean --kind gdb --path ...` first. Runners that read an existing
GDB input require that input to be restored first.

## WAVE reproduction

Rebuild runtime recordings in fresh scratch storage, then verify or restore
any manifest path (including copies and PCM/DAT reconstructions):

```sh
python3 tools/revkit/scripts/reproduce_wavs.py check-inputs
python3 tools/revkit/scripts/reproduce_wavs.py run --scratch /tmp/vtspeak-wavs
python3 tools/revkit/scripts/reproduce_artifacts.py verify --kind wav \
  --runtime-root /tmp/vtspeak-wavs
python3 tools/revkit/scripts/reproduce_artifacts.py restore --kind wav \
  --runtime-root /tmp/vtspeak-wavs --path tools/revkit/work/stage8/map-short.wav
```

Use `list` to inspect runtime batches and repeat `--batch NAME` to select them.
`verify --scratch PATH` rechecks completed runtime batches without executing
Wine. The artifact tool supports `--output-root PATH` and refuses changed
existing files. `clean --kind wav` removes only hash-matching materializations.
For the Stage 8, 9, and 11 offline verifiers, restore their WAVE inputs first;
the native Go Stage 8 test pins the original complete-WAVE hash directly.

The manifest records **1,600** disposable WAVE paths, including recordings
rebuilt by **149** runtime batches, duplicate copies, retained PCM, decoded DAT
segments, and exact sample compositions. Every local original was compared
against its reconstruction before pruning. The complete verification inventory
is in `wav-verification.json`.

The initial cleanup pruned **406 tracked research WAVs** and one untracked
runtime copy removed by the user: **407 local WAVs totaling 30,673,820 bytes**.
Rebasing that cleanup onto the remote history subsequently restored **1,187
WAVs and 919 GDB files totaling 802,850,305 bytes**. Those paths had already
been absent from the local parent tree, so their deletions were not part of
the commit replayed by rebase. The repair removes these materializations with
ordinary Git deletions. All 1,187 returned WAVs and 916 GDB files match the
manifest hashes; the other three GDB files are the previously omitted Stage 21
word-spacing, whitespace-class all-pairs, and oversized fullmask traces
documented in the [work directory retention boundary](../README.md).

No research WAV or materialized GDB files remain under `tools/revkit/work`;
vendor input WAVs under `binary/` are unaffected. This removes files from the
current tree; published historical commits still retain their objects.

The final 18 recordings required recovery of their actual inputs and complete
file layout. Historical shared-fixture interference explains several named
fixture mismatches. Three files combine audio from competing writers, including
PCM beyond their declared data lengths. Exact deterministic sample recipes
preserve their complete bytes. The [recovery evidence](investigation-main/README.md)
and sibling investigations record the texts, settings, component hashes, and
limits of these conclusions. `wav-replay-mismatches.json` retains the failed
attempts and records the verified resolution of every case.

### Runtime prerequisites

The runner uses Python 3, Docker, and the local Wine/GDB/Xvfb image built from
`tools/revkit/work/stage2-copy/Dockerfile`. The catalogue records the image ID
used for verification. After building a replacement image, pass
`--image vtspeak-stage2-wine:latest`; the recorded output hashes still apply.
The container has no network, mounts vendor inputs read-only, and writes only
inside its fresh scratch directory. It never uses the original research WAVs
as runtime synthesis inputs. Historical GDB source overrides preserve the
command version needed by the corresponding capture.

`wav-runtime-inputs.json` pins the local proprietary models, DLLs, overlays,
fixtures, and runners by SHA-256. `run` verifies these prerequisites before
launching Docker. These inputs remain required; a public checkout alone cannot
recreate proprietary-engine recordings. Existing extracted Kate MSI inputs
remain under ignored `corpus-parity/kate-msi/`; `extract_kate_installer.py`
can rebuild that package from the known installer without executing it, using
7-Zip and the recorded installer/package hashes. Do not alter vendor inputs
to satisfy the prerequisite check.

The James package DLL is a local-only copy at
`tools/revkit/work/wav-prerequisites/vt_jam.dll`, copied from
`Neospeech James/James Data and Program Files/Neospeech James/lib/vt_eng_james16.dll`.
Its expected hash is pinned alongside the other prerequisites. Scratch Wine
prefixes and temporary model copies are discarded after each batch; generated
WAVs and diagnostic logs remain in the chosen scratch directory.

The checked hashes establish exact reproduction in the tested local runtime.
They do not assert that another Wine/toolchain version produces the same
bytes, or establish whole-engine synthesis parity. Vendor inputs under
`binary/` and the voice-data directories are untouched. No Git history was
rewritten, and no commit or push was performed.
