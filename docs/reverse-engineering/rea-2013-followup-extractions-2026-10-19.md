# REA follow-up extractions for the 2013 VoiceText engine

## Scope

This pass used REA on the same read-only 2013 Paul PE32 DLL examined in the
[full decompilation report](rea-2013-full-engine-decompilation-2026-10-19.md),
SHA-256 `200945bbb2853cc56b3eaa03770eedf26066b20bfc471ef5b0213387035b37ce`.
It focused on information the 1,098-function pseudocode listing does not
provide by itself: resource structure, API-reachable call graphs,
cross-version function comparisons, and bounded value-flow graphs. Complete
REA records are in
[`tools/revkit/work/rea-2013-followup-2026-10-19/`](../../tools/revkit/work/rea-2013-followup-2026-10-19/).

### Loader API shape and cross-version comparison

In 2013, `VT_LOADTTS_ENG` is a one-block wrapper that calls
`VT_LOADTTS_EXT_ENG` with fixed arguments
`(param_1, param_2, param_3, 0, -1, param_4, NULL, -1)`. The 2006 DLL's
same-named `VT_LOADTTS_ENG` is a full 43-block function in Ghidra's dossier.
This identifies an API-shape change: the 2013 implementation places the
loader body under the extended export and keeps a compatibility wrapper at the
shorter name. It does not establish that the two loaders accept equivalent
data or have equivalent runtime behavior.

REA compared same-named `VT_TextToFile_ENG`, `VT_TextToBuffer_ENG`, and
`VT_LOADTTS_ENG` dossiers across the local 2006 Kate and 2013 Paul DLLs. The
named API identities matched, and their pseudocode, assembly, CFG, references,
and referenced names differed. Overall comparison status remained `unknown`
because callees are mostly autogenerated names and could not be aligned
safely; assembly text also lacks relocation normalization. Two explicit
internal pairs (`FUN_1001c860` / `FUN_10018c80` and `FUN_1001cff0` /
`FUN_10023350`) likewise remain unmatched by identity. These comparison
outputs identify candidates for manual version-specific study, not semantic
differences by themselves.

### G83 scoring and layout follow-up

REA value-flow traces were run on the previously identified score, shortlist,
prune, and backtracking functions. The individual graphs ranged from 76 to
2,224 nodes; the larger results required pagination and reported omitted
parameter bindings. Every serialized operation in these sampled traces had
`is_dead: true`, including operations in the recovered function bodies. This
output did not isolate a dependable G83-to-score dependency, so the established
runtime captures remain the stronger evidence and the G83 feature semantics
remain unresolved.

REA's recovered-type inspection at the exported version dword
`0x1007d6f8` returned `unavailable`: no exact database type or typed data is
defined at that address. It did not add a C structure or field schema. The
existing targeted Ghidra scalar scans and data-format scripts remain the
available evidence for their selected fields and tables.

## Evidence and remaining boundary

`evidence.json` preserves the resource-tree record, raw 988-byte read, and the
first call-path/value-flow set. `evidence-second-session.json` preserves the
expanded API paths, function dossiers, type query, and cross-version

No additional model field names, TPP class meanings, or G83 acoustic labels
were recovered. Those questions need independent semantic labels or further
controlled runtime evidence; assigning names from this static extraction
would exceed what it proves.
