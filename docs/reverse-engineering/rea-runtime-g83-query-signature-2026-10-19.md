# Runtime G83 query-signature trace (2026-10-19)

## Scope and method

This follow-up joins a controlled runtime intervention to the REA static
decompilation of the 2013 Paul engine. The input is the existing
`numeric-context-g83-can-anybody-help` Stage 5 fixture. The control records
numeric TPP code 83 at `FUN_1000e0c0`; the intervention replaces only that
argument with zero. Both runs then record the seven-byte signatures passed to
`FUN_10023dc0`, the direct class lookup. The reproducible GDB scripts and
runner are in [`tools/revkit/work/stage22/`](../../tools/revkit/work/stage22/).

REA examined `vt_pau.dll`, SHA-256
`200945bbb2853cc56b3eaa03770eedf26066b20bfc471ef5b0213387035b37ce`.
`FUN_10018770` constructs a seven-byte context signature and calls
`FUN_10023f90`; that selector dispatches to `FUN_10023dc0` for a direct class
lookup or `FUN_10023e70` for fallback. In the direct path,
`FUN_10023dc0` calls `FUN_10016ea0`, whose pseudocode constructs a five-byte
key as follows:

| Key byte | Signature source |
| --- | --- |
| 0 | `DAT_1007b7ec[sig[1]]` |
| 1 | `DAT_1007b788[sig[2]]` |
| 2 | `DAT_1007b850[sig[3]]` |
| 3 | `sig[5]` |
| 4 | `sig[6] & 0x20` |

The GDB breakpoints and returned registers show the signatures at the actual
class-query boundary. The analysis function names above are Ghidra autogenerated
names; the recovered control flow is pseudocode and may be imperfect.

## Observations

Both runs logged the code-83 token write and exited normally. Each captured 48
query signatures from caller `0x10023fca`. Comparing matching hit numbers:

- 41 of 48 signatures differ between control and intervention.
- The first difference is at hit 5, signature byte 5 (zero-based): control
  `0x22`, intervention `0x21`.
- Across all differing signatures, changed positions include signature bytes
  0 through 5. Byte 6 is zero in every one of the 96 records.
- Since `sig[5]` is copied to query-key byte 3, the observed changes at this
  position flow directly into one class-query key component. For these 96
  samples `sig[6] & 0x20` is zero.

Representative first differences:

| Hit | Control signature | G83-zero signature |
| ---: | --- | --- |
| 5 | `5a 2a 04 2d 18 22 00` | `5a 2a 04 2d 18 21 00` |
| 6 | `5a 46 04 2d 18 22 00` | `5a 46 04 2d 18 21 00` |
| 7 | `5a 2a 04 2d 18 21 00` | `5a 2a 04 2d 18 20 00` |

The control WAV hash is
`29052da3a11213f4616c30b2da31ccd9c4400d657afa1c163a51135653ddad09`; the
G83-zero WAV hash is
`f8aa3133ef5701e78f46db0bd55cdcf3674430c988d7b6f5834bd804a0683305`. These
match the existing Stage 12 effect outputs for the same input and intervention.
They therefore confirm the narrower capture did not change the previously
observed audio outcome.

## Interpretation and limits

This is new causal evidence that changing the numeric G83 token at the token
handler changes context signatures supplied to direct class lookup, including
the byte copied into key byte 3. It narrows the question from “does G83 affect
the engine?” to “what linguistic/acoustic distinction does this key component
encode, and which model records use it?”

It does **not** recover a semantic label for signature byte 5, any TPP
expansion, any model-field name, or an acoustic label from G83. Nor does this
single input and one-code intervention establish the complete effect across
contexts. Those meanings still require independently labeled examples or
additional controlled contrasts.
